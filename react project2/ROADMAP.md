# 향후 계획 — 함께 짜는 여행 코스

## 1. 문제 인식

현재 발길따라는 **한 사람이 AI가 제안한 코스를 받아 혼자 다듬는** 흐름으로 끝난다. 그러나 국내 여행은 대부분 여럿이 간다. 사용자 입장에서 코스가 완성된 다음에 실제로 일어나는 일은 "친구들에게 보여주고 의견을 받아 고치는 것"인데, 지금은 그 과정이 앱 바깥(메신저)에서 일어나고 수정 결과를 다시 앱에 손으로 옮겨야 한다.

즉 **AI 추천의 다음 단계인 '합의'가 비어 있다.** 이 공백을 메우는 것이 다음 마일스톤이다.

## 2. 검토한 두 가지 방식

### A안 — 실시간 공동 편집

여러 명이 동시에 같은 일정을 편집하고 변경이 즉시 서로에게 반영되는 방식(구글 독스 모델).

### B안 — 제안 기반 편집 (채택)

코스의 소유권은 만든 사람에게 두고, 초대받은 친구는 **"여기 추가하면 어때?" 제안만** 남긴다. 소유자가 수락해야 코스가 바뀐다(풀 리퀘스트 모델).

## 3. B안을 택한 이유

현재 구조에서 A안을 구현하면 **데이터가 조용히 사라지는 버그**가 구조적으로 발생한다.

**① 저장 단위가 코스 전체다.** 서버의 `SavedCourse` 는 일정 전체를 `payload` 라는 JSON 문자열 하나로 저장한다. 장소 단위 레코드가 아니므로 동시 저장은 마지막 저장이 이전 저장을 통째로 덮어쓴다(last-write-wins). A가 2일차 순서를 바꾸는 동안 B가 3일차에 장소를 추가하면, 나중에 저장한 쪽의 내용만 남고 **에러조차 나지 않는다.**

**② 소유 모델이 단독 전제다.** `SavedCourse` 는 `userId` 하나만 가지며 모든 조회가 "내 것인가"로 필터링된다. 공동 편집은 이를 "접근 권한이 있는가"로 바꾸는 전면 수정을 요구한다.

**③ 자동 정렬과 수동 편집이 충돌한다.** 앱은 이동 거리를 기준으로 동선을 자동 재정렬하며(`optimizeRouteOrder`), 사용자가 순서를 직접 바꾼 날은 자동 정렬에서 제외해 보호한다(`manualOrderDays`). 편집자가 여럿이 되면 이 보호 규칙이 무너진다 — 내가 맞춘 순서를 다른 참여자가 "최적화"로 되돌릴 수 있고, **누구를 기준으로 최적화할 것인가에 정답이 없다.**

B안은 이 세 문제를 **회피가 아니라 설계로** 해결한다. 제안은 추가만 되는(append-only) 기록이라 동시 입력이 충돌하지 않고, 코스 변경은 소유자 한 명이 순차적으로 수행하므로 기존 단독 소유 모델과 자동 정렬 규칙을 그대로 유지할 수 있다.

## 4. 설계 개요

### 데이터 모델 (신규 2개)

| 테이블 | 역할 | 비고 |
|---|---|---|
| `CourseShare` | 초대 링크 토큰, 만료 시각 | 코스당 1개, 재발급 가능 |
| `CourseSuggestion` | 제안 1건 (제안자, 날짜, 장소, 한 줄 사유, 상태) | 추가만 되고 수정되지 않음 |

`SavedCourse` 는 변경하지 않는다.

### 흐름

1. 소유자가 코스에서 **[친구 초대]** → 초대 링크 생성
2. 친구가 링크 접속 → 코스를 **읽기 전용**으로 열람
3. 친구가 장소를 검색해 **제안** 등록 (며칠차에, 왜)
4. 소유자에게 제안 목록이 쌓임 → **수락/거절**
5. 수락된 제안만 실제 일정에 반영

### 상태 전이

```
제안됨 → 수락됨 → 코스 반영
      ↘ 거절됨
```

제안은 삭제되지 않고 상태만 바뀌므로, **"왜 이 장소가 들어갔는지"의 기록이 남는다.** 이는 여행 후 회고나 커뮤니티 공유 시 그대로 활용할 수 있다.

## 5. 선행 과제

B안을 시작하기 전에 반드시 끝내야 하는 작업이 하나 있다.

**코스를 서버에 사는 데이터로 승격하는 것.** 현재 편집 결과는 브라우저 안에만 존재하며, 새로고침 시 유실을 막기 위해 로컬 스냅샷으로 보존하고 있다. 이는 단일 기기·단일 사용자 전제의 임시 방편이다. 다른 사람이 같은 코스를 열어보려면 편집 결과가 서버에 있어야 한다.

이 작업은 협업 기능을 하지 않더라도 **기기를 바꾸면 작업물이 사라진다**는 현재의 한계를 해소하므로, 독립적으로도 가치가 있다.

## 6. 단계별 계획

| 단계 | 내용 | 협업 없이도 가치 있는가 |
|---|---|---|
| 0 | 코스 편집 결과를 서버에 저장·갱신 | ○ (기기 간 이어보기) |
| 1 | 읽기 전용 공유 링크 | ○ (완성된 코스 자랑하기) |
| 2 | 제안 등록 | — |
| 3 | 수락/거절 및 반영 | — |

0단계와 1단계는 그 자체로 사용자 가치를 만들기 때문에, **협업 기능을 끝까지 못 가더라도 버려지는 작업이 없다.** 이 점이 단계 구성의 핵심 기준이었다.

## 7. 이번 범위에 포함하지 않은 이유

협업은 이 서비스에 남은 기능 후보 중 가치가 가장 높다고 판단했으나, 선행 과제(5장)를 포함하면 전체 작업량의 상당 부분이 화면이 아닌 구조 변경에 들어간다. 제한된 기간 안에서는 **기능을 절반만 완성한 상태로 남기는 것보다, 설계까지 확정하고 구현 순서를 명시하는 편이 낫다고 판단했다.**
